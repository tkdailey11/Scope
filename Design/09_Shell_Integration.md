# 09 — Shell Integration

## MVP shell support

Start with **zsh**.

macOS uses zsh as the default shell for modern user accounts, and limiting v1 to one shell keeps parsing and generation reliable.

Design the domain layer so Bash/fish support can be added later without rewriting the product model.

## File ownership strategy

Scope should own a dedicated generated file, for example:

```text
~/.scope/generated.zsh
```

The user's startup file should contain a small marked hook such as:

```zsh
# >>> Scope >>>
[[ -f "$HOME/.scope/generated.zsh" ]] && source "$HOME/.scope/generated.zsh"
# <<< Scope <<<
```

The exact filename/marker can change before shipping, but the behavior should remain narrow and obvious.

## Startup file choice

Do not assume `.zshrc` is always the only correct file.

Discovery should inspect relevant zsh startup files and explain what Scope intends to modify. For an interactive developer-focused MVP, `.zshrc` is the likely default hook location, but architecture should allow policy changes.

## Generated file structure

Keep output deterministic and human-readable:

```zsh
# Generated by Scope. Manual edits may be overwritten.

# Environment
export EDITOR='nvim'
export GOPATH="$HOME/go"

# PATH
export PATH="/opt/homebrew/bin:$PATH"
export PATH="$HOME/go/bin:$PATH"

# Aliases
alias gs='git status'
alias ll='ls -lah'

# Functions
mkcd() {
  mkdir -p "$1" && cd "$1"
}
```

## Quoting

Quoting is a critical correctness area.

Implement a dedicated escaping/serialization layer rather than string interpolation scattered through UI code.

Tests should cover:

- spaces;
- quotes;
- dollar signs;
- command substitution characters;
- backslashes;
- newlines where permitted;
- `$HOME` preservation when intentionally authored as an expandable expression.

Decide explicitly whether values are treated as literal strings or shell expressions. A good MVP may support a clear value mode rather than guessing.

## Validation

Before committing generated config, run zsh syntax validation using a non-interactive subprocess where possible.

Validation failures should block Apply and show actionable error context.

## Test shell

Testing should use temporary files and an isolated invocation rather than modifying production config.

The test shell should make it clear that:

- it is temporary;
- changes are pending;
- closing the test does not apply anything.

## Import parser

Do not attempt to build a complete zsh parser in v1.

Recognize high-confidence patterns such as:

```zsh
export NAME=value
alias name='command'
export PATH="...:$PATH"
name() { ... }
function name { ... }
```

Anything ambiguous should remain detected text rather than being transformed automatically.

## Backups

Before altering a user-owned startup file:

- create a timestamped backup;
- store metadata showing which file was modified;
- provide a Restore option in the app.
